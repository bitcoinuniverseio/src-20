Stamps,
SRC-20 and SRC-101.

Stamps is the Bitcoin meta-protocol and asset ecosystem. SRC-20 is its fungible-token layer, and SRC-101 is its name and record layer. This guide keeps their protocol facts, carrier formats, and product profiles distinct.

Stamps ecosystem
Keep the layers distinct
Stamps The umbrella Bitcoin meta-protocol for on-chain digital assets and the surrounding indexer ecosystem.
SRC-20 A fungible-token state machine interpreted from valid Stamps-compatible transaction data.
SRC-101 A name and record system with its own strict operation fields and lifecycle state.
Carrier format The on-chain transport changes by protocol era. It is not the same thing as the SRC-20 message schema.
Indexer state Deployments, supply, and balances are protocol interpretations, not Bitcoin consensus fields.
Start with the mental model

A token message is not enough on its own.

For SRC-20, the JSON, the transaction layout, the chain height, and the target indexer's rules combine to determine an outcome. A transaction can be valid Bitcoin, contain a valid Stamp payload, and still be an invalid SRC-20 state transition.

Bitcoin layer

Bitcoin confirms the transaction.

Bitcoin does not natively enforce ticker uniqueness, total supply, per-mint limits, or a fungible-token balance.

Stamp layer

The carrier is decoded and checked.

Compatible software recognizes a supported payload framing and carrier for the relevant protocol era.

SRC-20 layer

The indexer applies state rules.

The indexer validates the operation against deployed token data and the running address balances.

Important distinction A structurally valid Stamp can fail SRC-20 business rules. For example, an over-balance transfer does not change SRC-20 balances, even if the carrier itself is recognized as a Stamp.
Published protocol chronology

Do not collapse historical formats into one diagram.

The maintained Bitcoin Stamps indexer records distinct SRC-20 boundaries. Use the exact indexer release and block height you target when implementing historical parsing or crafting transactions.

BLOCK 788,041

Counterparty-era SRC-20

The first SRC-20 token is recorded in the official indexer's history as a Counterparty-era token.

BLOCK 793,068

Direct Bitcoin begins

The published history identifies this as the start of direct-Bitcoin SRC-20 transactions.

BLOCK 796,000

Counterparty cutoff

Counterparty SRC-20 transactions are no longer honored after this cutoff in the legacy documentation.

BLOCK 865,000

OLGA / P2WSH SRC-20

The maintained indexer describes SRC-20 adopting the OLGA P2WSH encoding at this boundary.

Chronology source: the maintained Bitcoin Stamps indexer README. Older prose describes the direct-Bitcoin transition less precisely, so this guide does not use a single 796,000 start date.

The canonical operations

Three messages, one stateful interpretation.

New integrations should emit compact UTF-8 JSON with lowercase protocol and operation values, quoted decimal strings, and only documented fields. Permissive historical parser behavior is not a portability target.

Deploy rule

First valid ticker deployment wins.

Ticks are case-insensitive identities. A duplicate deployment does not replace the indexed definition.

Mint rule

The state machine caps eligible mints.

The indexer caps a mint by the request, remaining supply, and the per-mint limit. A completely minted token cannot mint again.

Transfer rule

Insufficient balance invalidates the move.

A transfer above the indexed sender balance changes neither sender nor recipient SRC-20 balances.

Transaction-bound semantics

Addresses come from the Bitcoin transaction, not JSON.

The reference implementation derives ownership and routing from transaction position. Do not add a JSON "from" or "to" field and assume it authorizes or redirects a token operation.

Concept Reference interpretation Builder implication
Source / creator Derived from the spent output of vin[0]. Do not reorder inputs after selecting the intended source address.
Transfer recipient Derived from vout[0]. Place the intended recipient first, then review all later outputs separately.
Deploy creator Derived from the spent output of vin[0], not from an output. Keep the intended deployer at input zero. In the local profile, output zero is sender dust only and does not define creator identity.
Mint owner Derived from vout[0]. Put the intended credited minter at output zero before carrier and fee outputs.
Payload carrier Determined by the protocol era and target indexer. Use a tested library or a verified Universe profile. Do not hand-roll from a high-level diagram.
A safer integration posture

Build, inspect, observe, reconcile.

Protocol work is operational work. The signed transaction is the important artifact, and a completed broadcast is not the same thing as an accepted indexed state transition.

Choose the target indexer and era before implementation.

Pin an indexer release or SDK commit. Confirm its activation rules and test vectors before you decide which carrier a wallet will construct.

Resolve the ticker and state immediately before signing.

For mint and transfer, read the indexed deployment, supply, decimals, and current balance. Case-normalize the ticker locally for lookups.

Review the PSBT as a Bitcoin payment and a protocol event.

Check first input, first output, carrier outputs, change, miner fee, and every product fee. Never sign a third-party transaction only because its JSON looks familiar.

Verify indexed results after confirmation.

Store the txid and compare the target indexer's event, supply, and balances. Handle reorgs and failed semantic validation as normal outcomes.

Read the material that governs behavior

Source hierarchy, not cargo-cult copying.
