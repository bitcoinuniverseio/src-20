Authority order

Use the narrowest source that answers the question.

When a published explainer, SDK page, and source code disagree, do not average them. Choose the release-specific target indexer implementation and record the decision in the integration evidence.

1. Target indexer release

Acceptance behavior

For production, the actual release and its fixtures decide the decoding and ledger behavior you need to interoperate with.

2. Maintained protocol project

Current chronology and process

The maintained Bitcoin Stamps indexer documents protocol history, active components, and the SIP process.

3. Technical specifications

Message and carrier context

The Stamps SDK, OLGA specification, and OpenStamp documentation provide detailed compatibility and historical context.

4. Universe source tree

Product behavior

Local code documents the exact API, PSBT construction, fee configuration, and validation profile shipped by Universe.

Known documentation divergences

Resolve them explicitly, never silently.

The protocol has evolved. Historical sources remain useful, but a builder needs a concrete compatibility decision rather than a blended summary.

Topic What differs Documentation decision
Direct Bitcoin activation Older prose focuses on the 796,000 Counterparty cutoff. The maintained indexer chronology identifies direct Bitcoin at 793,068. Document both boundaries: direct Bitcoin begins at 793,068 and Counterparty SRC-20 ends after 796,000.
Current carrier Legacy descriptions use bare multisig plus ARC4. Maintained chronology identifies OLGA / P2WSH for SRC-20 from 865,000. Label bare multisig as a historical direct-Bitcoin path and P2WSH as the current maintained path. Pin the target indexer release.
Ticker characters Older material describes broad special-character and emoji behavior. Current implementations use a precise configured allowlist. Recommend one to five ASCII alphanumeric characters for new integrations and link the exact target configuration for wider support.
Numeric parsing Historical parser behavior can tolerate or truncate some forms that a strict builder should not create. Use quoted plain positive decimal strings, no separators, no exponent notation, and whole strings for max and lim.
State failure Some sources imply invalid SRC-20 operations never become Stamps. Current fixtures distinguish Stamp success from SRC-20 state failure. State that a semantic failure can preserve a recognized Stamp while producing no SRC-20 balance or supply change.

Update policy

Change docs with evidence, not after an incident.

A protocol-facing copy update can change user expectations. Treat it as an interface change and update it with the same discipline as a transaction builder change.

When an upstream release or SIP changes interpretation

Pin the source version, reproduce the change with a test vector, update the compatibility table, and add a dated note to the documentation changelog.

When Universe changes transaction construction, validation, or cost

Update the Universe profile, API reference, security notes, and conformance vectors in the same change. Do not leave a product fee or output-order change hidden in source code.

When sources conflict

Do not declare a universal rule. State the scope, link both sources, and describe the conservative product behavior until a target indexer release resolves the question.
