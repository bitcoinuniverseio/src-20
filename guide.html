An SRC-20 operation is only complete after the correct transaction confirms and the target indexer reports the intended state. This guide treats construction and verification as one workflow.

End-to-end workflow

Make every decision observable.

The sequence below is deliberately conservative. It prevents the most expensive failure mode: broadcasting a valid Bitcoin transaction that the intended indexer cannot recognize or cannot credit.

Pin the target indexer, carrier era, and network.

Record the indexer name, release or commit, mainnet or testnet, and the carrier format it accepts at the target chain height. The maintained Stamps indexer is experimental and protocol changes are coordinated through SIPs, so a release pin is part of the integration contract.

Resolve current state immediately before building.

For deploy, look up the case-normalized ticker. For mint, read the deployed maximum, per-mint limit, decimals, and remaining supply. For transfer, read the source address balance from the same indexer you expect to credit the transaction.

Create a strict canonical JSON payload.

Emit lowercase p and op, a compact object, and quoted decimal strings. Use only required fields plus deliberately supported metadata. Do not rely on parser repairs, number truncation, unknown fields, or a JSON address field.

Bind source and destination with transaction positions.

Make the intended source address control the first input. For deployment, that first input defines the creator. For mint and transfer, put the intended credited owner or recipient at output zero. The local deploy profile also uses sender dust at output zero, but that output does not define creator identity.

Use a tested carrier builder, then inspect its PSBT.

Construct the relevant era-specific carrier with a released library or the Universe profile. Do not turn a high-level decoder diagram into a home-grown production encoder without test vectors and indexer evidence.

Review every bitcoin output before signing.

Confirm output zero, the data outputs, change, miner fee, and every product service fee. Verify the network and address formats. A correct SRC-20 payload does not make unfamiliar outputs safe.

Broadcast, persist evidence, and wait for the right observation.

Store the exact JSON, unsigned and signed transaction identifiers where allowed, txid, timestamp, fee rate, and target indexer version. A mempool result is only a transport result. Wait for confirmation and then the target indexer's classification.

Reconcile state and communicate the actual outcome.

Read the indexer's event status, token supply, and both account balances. Tell the user whether Bitcoin confirmed, whether a Stamp payload was recognized, and whether SRC-20 state changed. Treat a reorg as a normal state to revisit.

Preflight checklist

Reject predictable failures locally.

Local validation does not create protocol consensus, but it saves users from paying for obvious mistakes. Reject a request before PSBT creation when any of these conditions fail.

  • The selected network, target indexer, carrier profile, and activation era match one another.
  • The ticker is one to five characters and follows the exact target indexer rules. Use ASCII alphanumeric ticks unless you have deliberate compatibility tests.
  • max and lim are positive whole decimal strings at or below 18446744073709551615.
  • dec is omitted or is an integer from 0 through 18.
  • amt is a positive plain decimal string that fits the deployed decimal precision and avoids exponent notation.
  • The token exists before mint or transfer, and the mint or transfer state has been refreshed from the target indexer.
  • The intended source or deploy creator can occupy vin[0], and the intended mint or transfer recipient can occupy vout[0].
  • All product fees are shown independently from the miner fee, and the final user-visible cost is based on the actual PSBT outputs.
PSBT review

Inspect the spend, not only the protocol intent.

Most wallet incidents are output-review failures. Present this review in the product before the wallet is asked to sign, and make it readable without requiring users to understand carrier bytes.

Inputs

Confirm the authority path.

  • The first input spends an output controlled by the address whose SRC-20 balance should be used.
  • Every additional input is expected and belongs to the user or an explicitly named funding flow.
  • Input selection has not accidentally spent a protected asset or unexpected UTXO.
  • The transaction is built for the expected Bitcoin network.
Outputs

Confirm the routing and cost path.

  • Output zero follows the local sender-dust convention for deploy, and belongs to the intended credited minter or transfer recipient for mint and transfer.
  • Data carrier outputs match the selected profile and do not replace the destination at output zero.
  • Change returns to the intended user address.
  • Every fee output has a named recipient, stated purpose, and amount in the review.
Never blind-sign a third-party PSBT. Official SRC-20 material warns that third-party transactions can include additional outputs that send BTC to an address the user does not control. Require an output-level review even when a trusted service prepared the event.
What the indexer can do

Explain caps and failures precisely.

Clear language avoids promising an exact post-state amount before a stateful indexer evaluates the event. The user should understand the intended amount and the valid indexed result.

Situation Expected state behavior Good product copy
Mint request exceeds lim The eligible result is capped by the per-mint limit. "The indexer may credit up to the token's per-mint limit, not the entire requested amount."
Mint request exceeds remaining supply The eligible result is capped by the remaining supply. "The indexer may credit only the remaining unminted supply."
Supply already exhausted The mint is an invalid SRC-20 transition. "Bitcoin may confirm this transaction, but the token is already fully minted."
Transfer exceeds indexed balance The transfer is invalid and changes neither account balance. "This transfer cannot be credited because the indexed source balance is insufficient."
Carrier recognized but state invalid Can remain a valid Stamp while failing SRC-20 state rules. "The transaction was recognized on-chain, but it did not create the requested SRC-20 ledger change."
Recovery and support evidence

Capture enough to reproduce an outcome.

A support request should be diagnosable without asking a user to expose seed phrases, private keys, or unnecessary wallet data.

Capture

Stable diagnostic data

Txid, network, chain height or confirmation count, target indexer version, action, case-normalized tick, requested amount, output-zero address, and event status.

Compare

Before and after state

Persist the preflight balance or supply snapshot and compare it with the post-indexed state. Use the same indexer for both readings.

Never request

Secret material

Never request a seed phrase, private key, signing secret, or a full wallet export. A txid and a redacted PSBT output summary are normally sufficient.
